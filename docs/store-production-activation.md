# دليل تفعيل المتجر والتراجع
آخر تحديث: 4 نوفمبر 2026. تابع [الخطة المرجعية](store-production-readiness-plan.md) و[حالة التنفيذ](store-production-implementation-status.md). هذا دليل المرحلة الثانية؛ لا يعني أن التفعيل تم.

تحديث 5 نوفمبر: [قائمة بيانات وإجراءات صاحب المشروع](store-production-owner-actions.md). لإعادة فحوص النسخة المحلية وتجهيز أرشيف الواجهة فقط: شغّل tools/store-release-check.ps1 من PowerShell، مع -ApiRoot و-PhpBinary عند اختلاف المسارات، و-OutputDirectory لمجلد أدلة جديد فارغ. يشغّل اختبارات API على SQLite في الذاكرة، ثم اختبارات الواجهة والبناء والمتصفح وفحص diff. يفشل فور فشل خطوة ولا ينشر ولا يشغّل Cron. دليل MySQL المتزامن منفصل. manifest.json داخل مجلد الأدلة يوضح أن المرشح محلي وغير معتمد للإنتاج؛ لا تتضمن الحزمة .env أو ملفات الخادم أو أسراره.

## قبل فتح البيع
- أكمل تحقق المرحلة الأولى في ملف المتابعة، واختبر نسخة مطابقة للإنتاج ببيانات اختبار.
- اضبط APP_ENV=production وAPP_DEBUG=false وAPP_URL وFRONTEND_URL بروابط HTTPS الصحيحة. المنطقة الزمنية التجارية BUSINESS_TIMEZONE=Africa/Cairo؛ مهام Hostinger تُدخل بتوقيت UTC.
- احفظ APP_KEY الحالي بأمان مع النسخ الاحتياطية. تغييره دون ترحيل التشفير يعطل قراءة الأسرار وأرصدة الوجهات المشفرة؛ لا تطبعه في السجلات أو Git.
- الاستضافة المشتركة: QUEUE_CONNECTION=sync. عند الانتقال إلى VPS اختر اتصالًا مثل database أو redis، وأنشئ worker تحت مدير عمليات مع إعادة تشغيله ومراقبته، وأبق Cron. تغيير المتغير وحده لا ينشئ worker.
- انشر ملفات composer.lock وpackage-lock.json المطابقة، وثبّت تبعيات الإنتاج وابنِ الواجهة. حدّث migrations ثم نظف/أعد بناء كاش الإعدادات والطرق حسب نشر Laravel المعتاد.
- حتى هذا التحديث توجد ترحيلات المتجر 1–15؛ شُغلت محليًا فقط. افحص artisan migrate:status على الخادم قبل فتح المتجر.
- فعّل الحساب الإلزامي وتوثيق البريد، واختبر SMTP المُعد في وحدة الإشعارات نفسها. لا تضع إعداد بريد موازية.
- اعتمد السياسات القانونية المنشورة والضرائب ونافذة المرتجع وبيانات الجهة البائعة. لا تُنسخ بيانات الاختبار أو نسب افتراضية إلى الإنتاج.
- راجع لكل بائع: الباقة والاستثناءات والمخزن وتكاليف الدفعات ووحدات البيع والعنوان وجهة الصرف وأسعار المحافظات. التكلفة المجهولة تمنع تأكيد خروج المخزون حتى تصحيحها.
- راجع السعر العام واستثناء البائع للشحن؛ الاستثناء يسبقه. لا يوجد سعر مجاني تلقائي لمحافظة جديدة. أدخل تكلفة الناقل الحقيقية؛ تخفيض رسم العميل لا يعني تخفيض تكلفة الناقل.
- الشحن اليدوي هو الموصل الحالي. تكامل API لناقل بعينه يحتاج اختيار حسابه والتحقق من عقده ومفاتيحه وخرائط المدن والحالات في Sandbox.
- شغّل php artisan store:readiness --launch واقرأ العوائق. الأمر يقرأ الإعدادات والترحيلات فقط؛ نجاحه لا يغني عن تجربة الاستضافة والحسابات الحقيقية.
- قرار 4 نوفمبر: الدفع الحقيقي مؤجل. لا تحفظ مفاتيح أو تجرِ تحصيلًا أو استردادًا حقيقيًا ضمن استكمال التطوير. يمكن تجهيز حسابات متعددة من الموصلات المدعومة عند استئناف التفعيل؛ لا يلزم اختيار بوابة واحدة لتصميم المتجر.

## الحسابات المالية
- أنشئ حساب بوابة الدفع من لوحة التحكم. اختبر المزود والحساب والبيئة والعملات والإشعارات الموقعة والاستعلام والاسترداد. اختبارات HTTP المحاكية لا تثبت صلاحية حساب تجاري.
- تعامل مع كل حساب مالي/بيئة بوابة كسجل مستقل. تدوير السر للحساب نفسه يختلف عن استبدال التاجر أو بيئة الاختبار بحساب إنتاج آخر.
- بيانات البطاقة لدى صفحة مزود الدفع؛ لا تُدخلها في قاعدة بيانات النظام أو السجلات.
- نجاح تحصيل العميل لا يثبت إيداع البوابة في البنك. وثق دفعة التوريد الفعلية ورسومها وضريبتها ومرجعها من «مطابقة الدفع».
- استرداد البوابة بعد توريد سابق يظهر تسوية سالبة لاحقة. تحويل العميل يدويًا من البنك لا يُخصم مرة ثانية من مستحق البوابة.
- الصرف المجدول ينشئ طلب صرف؛ اكتمال التحويل اليدوي يحتاج إثبات تنفيذ فعلي. لا يُدّعى وجود تحويل مصرفي آلي بمزود لم يُربط.
- افحص أول دورة حقيقية صغيرة: شراء، توثيق الدفع، تجهيز، تسليم، فاتورة، مرتجع، استرداد، توريد بوابة وصرف بائع. طابق دفتر المتجر مع البنك والمزود ودفاتر البائع.

## Cron واحد
1. عاين فقط: php artisan schedule:list --json. هذا يعرض الجدول دون تنفيذ الأعمال المستحقة.
2. راجع إعداد النسخ الاحتياطي والأعمال القديمة للإشعارات والتنظيف. تشغيل schedule:run قد يشغلها، بما فيها رسائل فعلية إن كانت القنوات مفعلة.
   تذكيرات ERP أصبحت محدودة وتعتمد outbox، مع تدارك سبعة أيام منذ التفعيل وإعادة فحص السداد قبل التسليم. رسائل WhatsApp المجدولة تتطلب مراجعة بدل إرسال آلي دون موافقة وقالب معتمد. إعداد WHATSAPP_API_VERSION مطلوب عند تفعيل تكامل WhatsApp؛ يُختار إصدار مدعوم لدى Meta وقت التفعيل ولا يُفترض إصدار قديم.
3. بعد النشر والتهيئة، أنشئ في hPanel مهمة كل دقيقة، مع استبدال المسارات بالقيم الفعلية:
   <PHP_BINARY> <PROJECT_ROOT>/artisan schedule:run >> <PRIVATE_CRON_LOG> 2>&1
4. لا تضف Cron مستقلًا لـ store:tick أو النسخ الاحتياطي بجانبه؛ كلاهما مسجل في جدول Laravel. مثال السطر الكامل لخادم يدعم crontab:
   * * * * * <PHP_BINARY> <PROJECT_ROOT>/artisan schedule:run >> <PRIVATE_CRON_LOG> 2>&1
5. تحقق من PHP CLI وإضافاته وذاكرته وصلاحيات storage وbootstrap/cache ومن منع الوصول العام إلى السجلات والنسخ. لا تفترض مسار PHP من جهاز التطوير.
6. تحقق من نبض المجدول بصفحة إدارة المتجر. في الوضع غير المتزامن تحقق أيضًا من نبض worker وزمن تأخره. يتوقف قبول الطلبات الجديدة في الإنتاج عند فقدان الصحة المطلوبة.
7. راقب المهام المتأخرة وmanual_review والأخطاء، ولا تعِد توثيق تحويل أو استرداد بمرجع جديد لمجرد تأخر الرد.
لا حاجة الآن إلى خدمة إيقاظ خارجية أو API إيقاظ عامة، لأن الخطة تدعم Cron.

## النسخ والتراجع
- احفظ قبل النشر نسخة كاملة من قاعدة البيانات والملفات المرفوعة وAPP_KEY والإعدادات والأسرار خارج المستودع والمسار العام. اختبر الاستعادة في قاعدة منفصلة.
- قبل التراجع أوقف استقبال الطلبات الجديدة وأوقف Cron والعمال، وانتظر المعاملات الجارية وطابق ما أُرسل بالفعل للمزودين.
- ترحيلات توسيع أنواع المحاسبة واستثناءات الشحن تحتفظ بالتوسيع في down منعًا لفقد UUID أو مستندات النظام أو استثناءات الأسعار. التراجع ليس أمر migrate:rollback أعمى؛ استعد النسخة المتوافقة أو نفّذ خطة بيانات مراجعة.
- لا تستعد لقطة قديمة ثم تعاود إرسال دفعات/استردادات حدثت خارج النظام بعدها. طابق المزود والبنك أولًا وحافظ على مراجع العمليات وعدم تكرارها.
- بعد الاستعادة راجع فك تشفير الإعدادات وحالات الطلبات وحجوزات المخزون وأرصدة البائعين والقيود وWebhook والأعمال المتراكمة، ثم افتح البيع تدريجيًا.
