# تحصيل أقساط العميل

الفورم المشترك `CustomerInstallmentCollectionDialog` يُفتح من ملف العميل، وقائمة إجراءات العميل، وزر أعلى سجل الخطط، وقائمة إجراءات أي خطة. البحث العام ينتقل إلى ملف العميل الموجود بالفعل، حيث يظهر زر التحصيل وفق صلاحية `installment_payments.create`.

- الاختيار الافتراضي: جميع الأقساط ذات متبقٍ حتى آخر يوم من الشهر الحالي، مع كل المتأخرات. تستخدم المقارنة المتبقي الفعلي من القسط الجزئي.
- التوزيع الافتراضي: تاريخ الاستحقاق ثم رقم الخطة ثم رقم القسط. يمكن تغيير الأقساط وتعديل مبالغ توزيعها يدويًا.
- الزيادة تتطلب اختيار أقساط إضافية. زر اقتراح توزيع الزيادة يُحدد أقساط الشهور القادمة للمعاينة فقط. لا يُحوَّل فائض إلى رصيد العميل تلقائيًا.
- تعرض المعاينة العميل، والتوزيع، والمتبقي من كل قسط. لا توجد كتابة مالية قبل التأكيد.
- تحصيل قسط واحد يستخدم المعاينة والتأكيد نفسيهما، مع إعطاء القسط المختار الأولوية داخل خطته، وتحذير واضح للدفع الجزئي أو توزيع الزيادة.
- التأجيل الرسمي وتعديل مواعيد الخطط خارج هذه الإضافة.

## عقد API

كل المسارات تحت `/api/v1`، وتلتزم بالشركة النشطة ونطاق الخطط والفروع والصلاحيات.

- `GET installment-collections/candidates?customer_id=...`: الأقساط المتاحة، `cutoff`، `due_total`، `total_remaining`.
- `POST installment-collections/preview`: `customer_id`, `installment_ids`, `amount`, `cash_box_id`, `payment_method_id`, `paid_at`، وحقول المرجع والملاحظات اختياريًا. يقبل `allocations: [{installment_id, amount}]` للتوزيع اليدوي. يعيد توزيعًا دقيقًا وتوكن معاينة مشفرًا صالحًا لمدة 15 دقيقة؛ لا يسجل أي دفعة.
- `POST installment-collections`: `token`, `request_key` (UUID ثابت لكل محاولة دفع). يعيد إيصالًا موحدًا يتضمن معرفات دفعات الخطط والتوزيع والمتبقي. إعادة نفس الطلب تعيد نفس الإيصال دون تسجيل جديد.

تُعاد مراجعة المعاينة تحت أقفال قاعدة البيانات. تغير الجدول أو انتهاء الشهر أو انتهاء صلاحية التوكن يستلزم معاينة جديدة. كل دفعات الخطط وحركاتها المالية وإيصال المجموعة داخل معاملة واحدة. فشل أي خطة يعيد العملية كاملة. عند انقطاع الاتصال تحتفظ الواجهة بنفس التوكن ومفتاح الطلب، وتتيح إعادة التحقق دون تكرار السداد.

تظل لكل خطة دفعتها ومعرف عمليتها المالية المتوافق مع السجل والعكس الحاليين، ويجمعها إيصال التحصيل. لا يضيف هذا التغيير إجراء عكس جماعي.

## التفعيل والتحقق

يجب نشر الباك إند وتشغيل migration `2026_11_23_000001_create_installment_collections_table` قبل نشر الواجهة. لا تعدّل migration بيانات الأقساط القائمة. يُستخدم توقيت التطبيق المكوّن لتحديد نهاية الشهر. لم يُشغّل هذا الترحيل على قاعدة بيانات التشغيل ضمن التطوير المحلي.

الاختبارات: `CustomerInstallmentCollectionTest` لاختبار التقسيم والدقة والعزل والتراجع وإعادة الطلب وحركة الخزنة الحقيقية؛ و`tests/e2e/installment-collection.spec.js` لتأكيد المعاينة وإلغاء الدفع والصلاحيات والهاتف. اختبارات المتصفح تستخدم API معزولة ولا تدفع بيانات حقيقية.

## التسليم المحلي والمراجعة

معرف التسليم: `HWNIX-INSTALLMENT-COLLECTION-20261124`. ملفات الحالة المعتمدة هي `docs/agent-handoff/HANDOFF.md` داخل المجلدين الأصليين للمشروعين؛ يتولى وكيل التشغيل كتابة `RESULT.md` بتكليف مستقل. هذه الوثيقة لا تمنح إذن رفع أو نشر أو ترحيل على قاعدة تشغيلية.

تجري حسابات التوزيع على الخادم باستخدام BCMath ومبالغ عشرية نصية، ويستمر استدعاء المحرك المالي القائم بعقده الحالي. لم تشمل الإضافة إعادة هيكلة الأنواع المالية في المحرك أو اختبار التزامن على MySQL؛ اختبارات SQLite المحلية تثبت التراجع وإعادة الطلب، ولا تمثل اختبار أقفال MySQL المتزامنة.

عند إعادة الكود للإصدار السابق مستقبلًا، لا تحذف جدول `installment_collections` بعد وجود إيصالات فيه، ولا تعكس دفعات أو تستعد قاعدة بيانات تلقائيًا؛ الأثر المالي المسجل يتطلب إجراءً وتفويضًا مستقلين. التراجع قبل أي سداد تجريبي يختلف عن معالجة عمليات مالية مسجلة.
